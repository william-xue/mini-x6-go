# Lesson 13.3 · 引脚的名称、类型与连接规则

## 要解决的问题

13.2 把引脚做成了可加、可删、可拖的"对象"，但它还是个**匿名点**：

```text
没有名字   界面上分不清哪个是哪个
没有类型   分不清输入还是输出，接错了没人拦
朝向是假的 法线靠"远离顶点平均质心"猜，凹轮廓会算反（实测已复现）
开放图形   被当成闭合处理，凭空多出一条并不存在的边
```

第一条是"说不上话"，后三条是**真的会画错**。

## 心智模型

引脚从"一个点"升级成"一个有身份的接点"：

```text
{ id, name, kind, x, y, u, v, normal, angle, direction, closed, shapeId }
        ▲     ▲                        ▲       ▲        ▲
        │     │                        │       │        └── 所在图形闭合与否
        │     │                        │       └── 离散档位（只给正交路由用）
        │     │                        └── 连续角度（朝向的真值）
        │     └── input / output / bidirectional
        └── P1、L_IN、TOP_OUT…
```

"身份"决定了第三件事有了意义：**哪两个能连**。

## 修掉的两个真缺陷

### 一、外法线：从"猜"改成"推"

13.1/13.2 沿用的是第 7.3 课那套：

```text
法线 = 边向量旋转 90°
正负 = 看它跟"顶点平均质心 → 落点"是否同向
```

它对**星形**轮廓成立，对凹轮廓必错。实测（窄槽外壳，材料在槽壁左侧）：

```text
槽内壁 x=340 的正确朝外方向 = (+1, 0) = right
7.3 的实现返回的是        (-1, 0) = left      ← 引出线会往元件肚子里走
```

13.3 换成**绕向**：

```text
① 先算鞋带和的两倍 signedAreaTwice(points)
     > 0  → 边向量 (dx,dy) 的垂线 (dy,-dx) 指向外侧
     < 0  → 反过来
② 朝外方向只取决于"轮廓是怎么绕的"，不需要任何质心假设
```

实测（同一条凹槽外壳）：

```text
上边朝外 = (0,-1)  ✓
右外壁朝外 = (+1,0) ✓
槽内壁朝外 = (+1,0) ✓   ← 修好了
槽底朝外 = (0,-1)  ✓
```

顺带得到一个更强的性质：**轮廓反着绕，同一堵墙的朝外方向不变**。
因为边向量反向时垂线跟着反向、绕向符号也反向，两次翻转正好抵消 —— 这正是绕向法比质心法稳的地方。

### 二、开放图形：不再凭空多出一条边

7.3 的 `nearestPointOnOutline` 用 `% 点数` 取模，等于给任何折线补一段"末点 → 首点"。
对只有一段的 `<line>`，补出来的正好是它自己那一段，所以看不出问题；
**多段 `polyline`、无 `Z` 的 `path` 就露馅了**。实测（纯线条简图素材）：

```text
点 (520,152) → 引脚落在 (518.5,154.7)，离点击处 3.0   ← 那个位置素材里什么都没有
```

13.3 的做法：

```text
开闭不用看 Z 标记，看几何事实：首尾两点是否重合  pointsFormClosedLoop(points)
closed = false 时，最近点搜索只走真实存在的那些段
```

并且给"朝外方向"一个诚实的处理：

```text
闭合图形  direction = 4 向档位，angle = 连续角度
开放图形  direction = null（它两边都是外面，硬给一个是假的），angle 仍给出
```

实测（同一条折线）：

```text
点 (520,152) → 距离 49.5，落在真实的那两段上；direction = null
```

## 连接规则

```text
双向 = 通配
输入 ↔ 输出  = 可以
输入 ↔ 输入、输出 ↔ 输出 = 不行（最常见的一类接错）
同一个引脚接自己    = 不行
同一对引脚连两次    = 不行（正着反着都算同一条）
定义里找不到那个引脚 = 不行，并说清楚原因
```

规则写成纯函数（`validateConnection`），装配交互只在**建边之前**插一道闸门：
拒绝就只把理由交出来，不建边。

实测（真指针事件驱动装配画布）：

```text
① OUT1 → OUT1    拒绝  类型冲突：OUT1（输出）不能接 OUT1（输出）   边数 0
② OUT1 → IN1     允许  OUT1（输出）→ IN1（输入）                   边数 1
③ 同一对再连一次  拒绝  这两个引脚之间已经有一条线了                 边数 1
④ 反过来连同一对  拒绝  这两个引脚之间已经有一条线了                 边数 1
```

纯函数（可单测）：

```js
signedAreaTwice(points)              // 绕向
pointsFormClosedLoop(points)         // 开闭
outwardNormal(points, index, closed) // 朝外法线
nearestOnShape(points, point, closed, maxDistance)

kindsCompatible(a, b)
```

## 关于"4 向截断"

有人会问：斜边上的引脚是不是还被截断成"左/右"？

```text
引脚朝向的**真值**是 angle（连续角度），stem 就沿它画 —— 斜边上就是斜的
direction 只是给**正交路由**用的离散档位，不再是"引脚朝向"的唯一表示
```

要让路由也沿斜边引出，改读 `angle` 即可 —— 那是路由层的事，不属本课。

```text
13.1  读轮廓                    ← 原样继承
13.2  加 / 删 / 拖 / 缩放跟随     ← 原样继承（交互状态机完全没改）

```

## 已知局限

1. **还是没有撤销**（依赖第 9 课 9.2）。
2. **路由仍只认 4 向**：斜边引脚的正交走线还是横平竖直 —— 读 `angle` 才能表达斜向引出，属路由层。
3. **类型只做"相容性"判断**，没有电气语义（电压等级、极性、载流能力）—— 那是产品层。
4. `<text>` / `<image>` / `<use>` 仍然读不了（13.4 处理）。
